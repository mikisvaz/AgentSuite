## Open design points

(Worker memo, 2026-11-02, from the staged evidence register `new_doctrine/work/v7-evidence-register.md` and the pinned mandate `new_doctrine/work/v7-mandate.md`. Defaults and tensions stated; final decisions belong to Manager.)

### a. Analyst: new permanent role vs Worker variant

- Mandate default: mandate §4 "Define or revise a role for general-purpose computational work, consistent with the current AgentSuite design" — explicitly either; the restated request adds "no new permanent agents beyond the Analyst (if absent)" and "default is whichever the delivery matrix supports with least added roster weight".
- Tension: a new directory adds roster weight (society roster, delivery matrix, context surface) for what is largely a *contract*, not a capability gap — Worker already has Bash/Python/Ruby; but the mandate's Scout-agnostic default toolset (no broad Scout access) is the opposite of Worker's full-tooling surface, so a Worker variant would need a per-bout tool restriction that the current chat syntax cannot express (tool blocks are per-agent, not per-brief, except via `cortex_brief` tool specs).
- Recommendation: create a minimal `Analyst/` role whose start_chat is a strict computational contract (staged input package + manifest, read-only inputs, designated results area, reproducible transformations, the mandate's honest "prompt prohibition is not a security boundary" statement) and whose tool block is general compute only — because the contract is enforceable only via the per-agent tool surface, and a Worker variant would smuggle the full toolset in every launch.

### b. Cortex-optional verdict vs blanket read-only Cortex grant in the doctrine footer

- Mandate default: §2.F "Cortex is optional infrastructure... Do not create pointer artifacts that nobody consumes, duplicate files without purpose, or route evidence through Cortex when an ordinary project artifact is sufficient."
- Tension: `Agent/doctrine` ends with `introduce: Cortex` + three read-only `tool: Cortex` lines, and every agent importing the doctrine gets that grant (the footer says "All agents following this doctrine have access to read the Cortex"). Optionality-as-discipline conflicts with grant-by-default: an always-present tool invites always-used patterns (the pointer-artifact failure mode the audit flagged), while trimming the footer loses the recall affordance that doctrine §2 legitimately wants ("check reviewed project documentation, research/, and relevant Cortex state").
- Recommendation: keep the doctrine footer read-only grant as-is (read-only recall is the low-risk half and matches doctrine §2) and encode the optional *write* side in role contracts: Research curates, Worker/Analyst write only when the task asks or the finding is reusable (already Worker's current text). Reason: the failure mode RB-2/E cites is pointer *artifacts* and mandatory routing, both write-side; a footer trim would be doctrine churn without evidence.

### c. Home of the branch-consumption report template; which roles emit it

- Mandate default: §5 defines the template and says "Use this compact structure for any branch whose execution may affect a subsequent implementation or scientific decision... The Manager must carry relevant entries into ScientificLead review" — it does not fix the file.
- Tension: the template is collaboration mechanics (a handoff format), so the collaboration guide is its natural home; but it must also be *behaviorally present* in the emitting roles' start_chats or it will not be emitted (the audit's RB-1/RB-4 episodes were exactly missing propagation between Manager and Lead, not missing templates). Duplicating full text in many role files is boilerplate bloat (RB-4 also flags 130k chars of re-sent boilerplate).
- Recommendation: template lives once in `doctrines/collaboration` (or its v7 successor); emitting roles get a two-line binding ("every consequential branch return follows the collaboration guide's branch-consumption report; Manager carries entries into Lead review") rather than a copy. Emitters: Analyst, Investigator, Worker, ScoutCoder (any branch that consumed/rejected an interface); Manager relays; no one else.

### d. Investigator vs Analyst overlap (one-paragraph line-drawing)

- Mandate default: §4 "Retain and revise Investigator, Worker, Reader... only where they have a distinct purpose" and the Analyst section "should not implement Scout tasks, entities or workflow infrastructure".
- Tension: Investigator is the scientific-question executor with the full Worker surface and evidence-chain obligations; an unqualified Analyst could become a second executor for the same questions (roster bloat, role confusion — the mandate's roster-weight watchpoint).
- Recommendation: draw the line at *what the role owns, not which tools it runs*: Investigator owns a scientific question and its evidence chain (may compute in service of the question, with domain tooling); Analyst owns a computation package (input manifest + reproducible transformation) and returns results plus a computational contract — it never frames, interprets, or adjudicates scientific claims, never selects the question, and never curates evidence. In practice: if the output is "an answer to a scientific question", it is Investigator's; if it is "numbers reproducibly derived from staged inputs, interpretation deferred to Research", it is Analyst's. Investigator may *request* Analyst runs; Analyst never initiates investigation. This keeps one executor per question and one executor per computation, with no competing ownership.
